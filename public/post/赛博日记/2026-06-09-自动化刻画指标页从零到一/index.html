📝 今日概要#

产品化突破日。 从零搭建了自动化测试效能度量体系（覆盖率/通过率/修复时长三大指标），完善了总览页面的权限管控与负责人维度统计，并为 Web 自动化引入了延迟重试机制——今天的每一行代码都在回答"如何让自动化质量变得可量化、可管理"。

🔍 核心技术进展#

1. 自动化刻画指标页面（全新页面，从 0 到 1）#

  • 来源：Cursor 会话 18:17 / claude_2026-06-09.md
  • 三大核心指标落地：
    • 核心场景覆盖率：按模块统计 已整理/全部，模块取 回归-稳定的|APP| 或 PC| 下一级目录名
    • 平均通过率：通过标签数 / 已整理标签数，模块通过率 <50% 排除出平台平均（抗极端值）
    • 平均修复时长：用例标签从「未通过」→「通过」的时间差自动记录，替代手工录入
  • 后端新增 TestCaseRepairEvent 表 + Prisma 迁移，在 test-cases.service.ts 中 hook 标签变更事件自动计时
  • 前端 AutomationMetricsView.vue + MetricsBarChart.vue（echarts 水平柱状图 + 90% 目标线）
  • 目标值可编辑，存 localStorage

2. 总览页面权限体系重构#

  • 来源：Cursor 会话 12:05 / claude_2026-06-09.md
  • 纠正了"admin 账号 = 管理员"的错误理解，对齐项目已有的 admin_accounts 白名单 + AdminGuard 体系
  • 新增第 4 模块「用例完成情况」：APP+PC 合并为一张按负责人的汇总表，仅白名单用户可见
  • 导出功能：仅管理员可导出「已整理但未通过」用例 CSV（与用例库导出模板一致）
  • 管理员数据拆为独立接口 POST /api/automation-metrics/owner-completion，普通 summary 接口不泄露敏感数据

3. 测试计划「全部添加」功能#

  • 来源：Cursor 会话 12:05 / claude_2026-06-09.md
  • 分页拉取所有搜索结果（每页 100 条），自动去重，toast 提示实际添加数
  • 解决了之前"超过 30 条必须手动缩小范围"的痛点

4. Web 自动化延迟重试机制#

  • 来源：2026-06-09.md 技术笔记
  • 判断失败后等 2s 重试，覆盖 Web 预期校验、点击校验、App 步级 AI 裁判
  • 环境变量可控：YSB_WEB_JUDGE_RETRY、YSB_WEB_JUDGE_RETRY_DELAY_SEC

💡 深度洞察与经验教训#

  • 洞察：修复时长的自动追踪（标签变更 hook）比手动填表准确得多——好的度量不需要人参与，它应该是工程行为的副产品。这个思路可以推广到更多质量指标。
  • 教训 1 — 统计口径要精确对齐用户预期：田庆宏有「通过」标签的用例没被统计，根因是缺少「已整理」标签。口径文档必须提前确认：哪些标签组合才算"进入统计池"。先定口径，再写代码。
  • 教训 2 — 路径解析别想当然：库中实际路径是 回归用例|回归-稳定的|APP|…，不是从 回归-稳定的 开头。用 startsWith 导致全军覆没。查数据库确认实际数据格式，再决定匹配策略。
  • 教训 3 — 权限 ≠ 账号：用户指出"admin 权限和 admin 账号是两回事"。项目中已有成熟的白名单 + Guard 体系，实现前应先充分调研现有权限架构，而非自创一套。
  • 教训 4 — 延迟重试是自动化的必需品：点击校验失败可能是误报（页面未刷新完），2s 等待后再验一次就能消除大量假失败。自动化中"快"不如"稳"。

🚀 未来行动设想#

  • 修复时长增加中位数、P95 分位数统计，避免极端值拉偏平均数
  • 覆盖率增加趋势折线图（近 30 天），让覆盖变化可追溯
  • 延迟重试时间和次数做成前端设置页可配置项，减少改环境变量的运维成本
  • App + PC 测试计划并行执行：增加全局执行队列或跨轨冲突检测，当前串行效率有瓶颈
  • 测试计划通过后自动打「已整理」标签（或提供批量操作），解决标签口径不一致的问题
