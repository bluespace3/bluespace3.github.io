PP3 三卡混插推理实测（2×170HX + 1×5060 Ti，FlashNext 176B NVFP4）

  • 权重按 safetensors header 逐 tensor 扫描（非估算）：总 125.87 GiB；PLE 表 47.75 GiB 走 mmap 在 RAM、不占显存；显存权重约 78 GiB = MoE 专家 63.28 + attn/GDN 4.48 + MTP 4.86 + lm_head 1.18 + embed 1.18 + 视觉 0.84 + 其他约 2.3；单主干层约 1.41 GiB
  • 精准切分结论：8G 的 5060 Ti 塞不下末级（MTP+lm_head 合计 6.04 GiB），当中间层会撞 full_attention 层 fa2 无 sm_120 的问题；唯一正确做法是 5060 Ti 当首级、只承载 linear_attention 层——embed 1.18 + 视觉塔 0.84 + 2 层 GDN 2.82，合计 4.84 GiB，不碰任何 FA 内核；MTP6 留 170HX 末级，KV 池不受小卡拖累
  • 分区由 2/23/23 修正为 3/22/23：PLE 层 ids 是 1-based、分区边界是 0-based，首分区必须 ≥3 层（layers [0,3)）；CUDA_VISIBLE_DEVICES=2,0,1
  • 内核可用性核查：torch 2.13+cu130 arch_list 含 sm_120 ✓；triton 3.7.1 在 5060 Ti 实测 JIT+执行 ✓；vllm _C/_moe_C .so 含 sm_120 SASS ✓；fa2 仅 sm_80、fa3 仅 sm_90 ✗；VLLM_PP_LAYER_PARTITION 支持手工切分（个数==pp_size、总和==48 校验在位）
  • 脚本落地（均过 bash -n 语法检查+试运行验证）：start-nvfp4-pp3-test.sh 从生产启动器逐字复制、只改并行布局四项，自带 rank0 必须 sm_120 断言+分区总和校验；pp3-test-run.sh 单窗口编排：停 Basalt → 等显存回收 → touch kmine-paused → systemd-run 瞬态 unit 启动 → 按 pid 核验 cmdline 含 pipeline-parallel-size 3 → 打印 KV 池 → 冒烟 → 3 轮 decode 基准（与 PP2 同口径 1500tok）
  • 实跑结果：rank0（5060 Ti）权重装载成功（PLE mmap 挂上、Marlin FP4 weight-only 路径）；rank1（170HX）33.5 GiB 装载成功；rank2（170HX 末级）建 MTP 草稿模型时 f.get_tensor 报 UntypedStorage。另发现 expandable_segments:True 与 safetensors lazy 零拷贝装载路径冲突（170HX 不需要它——之前 OOM 是因 lm_head 未剥离，现已剥离）
  • 收尾定性：NVFP4 主干必须走 marlin（全局 moe_backend 一个值管所有 MoE 层，triton 会把 NVFP4 也否掉）；根修方向是 _supports_current_device 的 capability 探测在 EngineCore/混合架构下看错卡——给 flashinfer_cutlass 设备探测加「任意可见卡不达标即拒绝」守卫，混合组 170HX 不支持 cutlass 时自动落 triton/marlin
  • 风险按概率排序：Marlin FP4 在 sm_120 首次实际运行 → 跨架构 NCCL（sm_80↔sm_120 无 P2P 走 SHM）→ async-scheduling+PP3+MTP 混合批次竞态（pp_utils 补丁只在 2 rank 验证过）；sm_120 首跑含 triton/inductor 冷编译、启动可能 10-25 分钟（就绪上限已给 30 分钟），预计总窗口 40-60 分钟，结束要么留 PP3 观察要么一条命令回滚 Basalt
