# Jev 决策模型在网页 UI 自动化中的价值：双用例五方案实测

> 实测日期：2026-09-23 ~ 09-24 · 环境：某医药电商测试环境（已脱敏）
> 起因：公众号展示"Jev 决策 + 小模型规划"的网页自动化范式，并称通用小模型 laya 可平替 Jev。本基准验证两件事：**Jev 的价值到底在哪，以及 laya 能不能接棒**。
> 模型规格：文中"bu-30"指 `browser-use/bu-30b-a3b-preview`——**30B 总参的稀疏 MoE，每 token 激活约 3B**，本机双卡 vLLM 部署；后文"小模型"均指这种激活 3B 量级的方案。测法：同执行器横比，每方案 n=5，全轮 pass 才计均时，失败轮不剔除。

## 一句话结论（全部有数据兜底）

**Jev 的价值 = 让激活 3B 量级的稀疏小模型直接具备生产可用的网页操作能力**：同一个 bu-30，自己选元素 0/15，挂上 Jev 两个用例双双 5/5、50 次决策置信度全部 ≥0.85。它的边界同样清晰：**大模型在场时 Jev 零增益**——deepseek 直选同样 5/5 且略快。laya 平替 Jev 的设想被证伪。

## 基准设计

四层架构，五组方案只换"规划模型 × 决策层"这一个变量，判据、安全闸、执行器逐行相同，各 n=5：

1. 规划层：LLM 把意图拆成步骤（action / what / value）
2. **决策层（被比较变量）**：每步（英文动作描述 + 元素清单）→ 目标元素编号
3. 执行层：Playwright 确定性回放
4. 判定层：代码硬断言（URL 特征 + 页面关键文本双条件），绝不问 LLM 成没成

- **用例一** 短信登录（4 步短任务）
- **用例二** 采购链路（10 步长任务：搜索→悬浮加购 3 件→结算→采购金支付，判据含订单数 +1 外部双证）

## 结果总表

**用例一：短信登录**

| 方案 | 准确率 | 均耗时 |
|---|---|---|
| bu-30 + **Jev** | 5/5 | 12.2s |
| deepseek + **Jev** | 5/5 | 12.7s |
| deepseek 直选 | 5/5 | 11.8s |
| bu-30 + browser-use | 5/5 | 15.9s |
| bu-30 + **laya** | **0/15** ❌ | 4.4s 即崩 |

**用例二：采购链路（10 步）**

| 方案 | 准确率 | 均耗时 | 10 步决策合计 |
|---|---|---|---|
| bu-30 + **Jev** | 5/5 | 34.9s | 11.2s（≈1.1s/步） |
| deepseek + **Jev** | 5/5 | 41.6s | 10.3s |
| deepseek 直选 | 5/5 | 41.8s | — |
| bu-30 + browser-use | **迷失** ❌ | — | 94+ 步未到结算 |
| deepseek + browser-use | 5/5 | 49.7s | — |

最后两行是 Jev 价值最硬的反证：**同一个 bu-30**，在 browser-use 里自主边看边选，长链条直接迷失——94+ 步反复重启搜索、幻觉自造网址、飘去无关频道打圈；挂上 Jev 后同一模型 10 步一次不错走完。说明长任务崩的不是"模型会不会操作"，而是"每步选元素的活有没有人接管"。换 deepseek 走 browser-use 能通关（5/5），但 49.7s 全场最慢、每步全页 DOM 上云——"强模型硬扛"路径既贵又慢，Jev 把这段能力下放给了激活 3B 的稀疏模型。

## Jev 价值的四条实证

### 1. 对照组证明：没有专用决策层，小模型玩不转网页
laya（公众号点名的"平替"）在同一执行器上 **0/15**，三变体（english/multilingual/typed-decisions）各 0/5。崩法很有代表性：放着明显的 `[4] <input> 手机号码` 不选，去选 tab 和 div；且**错选置信度 0.33 反而高于正确答案的 0.15**——置信度门控救不了它。192 条裸决策底稿显示最好变体也仅 56%。后续对照实验定案：低准确率主因**不是中文**，是没有"网页状态→选元素"训练数据导致的判别式先验坍缩。

### 2. 同一小模型 + Jev = 立刻 5/5，且长任务不退化
bu-30 挂 Jev 后 4 步登录 5/5、10 步采购也 5/5；用例二两批独立复跑均值均 34.9s，可复现性坐实。全场 50 次元素选择（10 步 × 5 轮）**置信度最低 0.85**，无一选错——规划层负责"做什么"，选元素的"在哪做"全部交给 Jev，小模型的短板被整个绕开。

### 3. 跨语言匹配是隐形刚需
规划层输出**英文**动作描述（"click quantity increase button"），页面元素全是中文。Jev 在英文动作→中文元素的清单上 conf 稳定 0.85~1.0。这不是锦上添花：bu-30 这类小模型生成中文会乱码，英文提示词是唯一可靠姿势，决策层必须扛住跨语言——这正是"小模型+Jev"组合能成立的前提。

### 4. 成本结构：便宜到可以按步计费
单次决策约 $0.00002（用例二一整单 10 次决策 <$0.0003）；Jev 原生决策延迟仅 35~80ms，基准中实测 ~1.1s/次的大头是代理网络税，部署位置合适还能再压一个量级。且每步只上送 25 条元素标签 + 一句英文动作——对比"每步把全页 DOM 喂给大模型"的 agent 方案，上下文体积差着量级（本基准未单独计量 token 费用，此为结构对比）。

## Jev 的诚实边界：大模型在场时它是零增量

- 登录用例：deepseek 直选 11.8s **比** deepseek+Jev 12.7s 还快 0.9s——多交一次 API 网络税，没有换回任何准确率（两边都 5/5）
- 采购用例：C 41.6s vs D 41.8s，打平
- 结论：**决策层的强弱只在"规划模型自己选不准"时才兑现价值**。有强模型 API 且不在乎成本，直选即可；Jev 面向的是成本敏感、边缘部署、小模型为主的场景

## 选型建议

| 场景 | 建议 |
|---|---|
| 成本敏感 / 边缘 / 激活 3B 级稀疏模型 | 稀疏小模型规划 + Jev 决策（本实测：全场最快 34.9s，规划本地免费） |
| 有强模型 API、不在乎 token 成本 | 大模型直选，不必加 Jev |
| 想用 laya 类通用小模型做决策层 | ❌ 证伪，仅限其训练域（文本分类/分流） |
