## 🔍 核心技术进展

### 1. 企微日报 AI 分析流程重构（后端）
将原本「日报顺带抽样分析少量失败样例」的设计，改为**发送前先全量分析再推送**的串行流程。核心改动：
- AI 分析从 `highlights 循环内调用` 提取为独立阶段 `xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`，只分析 `ai_likely_bug IS NULL` 的记录，避免重复请求
- 分析上限从 **1 条** → **50 条**（线上配置 + 硬编码上限同步调整）
- 通过率口径重新定义：疑似 Bug = 仅 `ai_likely_bug = 1`，NULL 不计入分子（等于 NULL 视为「待定/无嫌疑」）

### 2. 运行失败日志体验优化（前端 + 后端）
- 新增 `POST /api/automation-metrics/failure-records/analyze` 接口，前端「AI 判定」列为空时支持**点击手动触发分析**
- 排序逻辑修正：从 `ORDER BY run_at DESC` 改为 `ORDER BY failure_count DESC`，真正按失败次数排序
- 分页从 20 → 10 条/页；用例完成情况对所有登录用户开放（移除 AdminGuard）

### 3. NestJS 部署故障 → 修复（硬核 Bug）
**故障链**：给 `AutomationMetricsFailureService` 新增 `FailureBugAnalyzerService` 依赖 → 只在 `AutomationMetricsModule` 补了 provider → `UiAutomationDashboardModule` 和 `WeComModule` 也各自注册了该 Service 但缺依赖 → 容器启动即崩溃 `Restarting (1)` → `docker compose up --build` 显示成功，但容器无法运行。

**修复**：创建 `FailureBugAnalyzerModule` 共享模块，在三个使用处统一导入。

### 4. Windows 工作站磁盘清理
清理 uv 缓存（8.4 GB）、Playwright（3.7 GB）、pip/Nuitka/node-gyp 缓存，C 盘可用空间从 12.8 GB → 26.38 GB。

## 💡 深度洞察与经验教训

- **洞察：编译通过 ≠ 运行可用**。NestJS 的 DI 容器在 `nest build`（TypeScript 编译）阶段不会实例化，依赖图谱错误只在真正 `NestFactory.create()` 时才暴露。Docker 镜像构建成功只说明代码能编译，不代表应用能启动。这是动态依赖注入框架的「编译-运行时鸿沟」。

- **洞察：Service 多 Module 重复注册是架构债**。同一个 Service 在多个 `@Module.providers` 里各注册一份，意味着每个 Module 会创建独立实例。一旦给这个 Service 加新依赖，就得在所有注册点同步补 provider——违反单一数据源原则。

- **教训：部署后验收是硬性环节，不是可选项。** 今天的事故完全可以被部署脚本拦截——只需在 `docker compose up` 之后加一步 `docker compose ps` 检查容器状态 + `docker compose logs` 搜索 `successfully started`。已将此规则写入部署 Skill 的历史教训和验收清单。

- **教训：AI 统计口径要和 AI 分析覆盖度对齐。** 之前 `NULL ≠ 0` 即计入疑似 Bug，但大量 NULL 记录从未被 AI 看过——等于把「不知道」当成了「有嫌疑」，统计偏差严重。修正后的口径：只有 `ai_likely_bug = 1` 才算疑似 Bug，更诚实。
